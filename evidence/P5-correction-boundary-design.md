# P5 — Correction boundary design checkpoint

Status: Read-only inspection complete; awaiting Sol review. No P5 product code has been edited.

## Current boundaries

| Work item | Current correction/retry owners | Budget and checkpoint owner |
|---|---|---|
| Learn/Print capability authoring | `AuthoringEngine` parses JSON, validates its JSON Schema and registered validators, and sends up to two semantic repair prompts. `LLMAuthoringProvider` also asks `run_structured_agent` for one pydantic-ai output retry; the V3 `run_llm` retry policy adds provider attempts (default one retry for the block-writer node). Those nested calls are invisible to the AuthoringEngine budget. | `native_execution` restores `CallBudgetLedger` and `CheckpointStore` from the output Generation state and its reliability persistence hook saves reservations/checkpoints. Work-order IDs key the individual interaction/node tasks. |
| Learn document primitive | `AuthoringEngine` repairs schema/registered-validator failures. Then `document.writer` runs `_payload_quality_errors` outside the engine, marks the checkpoint ambiguous, and raises `INVALID_PAYLOAD`; the quality findings cannot consume the remaining same-item repair budget. Pydantic normalization is another post-engine check. | Same per-item ledger/checkpoint passed from `native_execution`; `node:<work_order_id>` checkpoints only after normalized content succeeds. |
| Learn interaction | `AuthoringEngine` handles schema and registered config validators. `interaction_contract_from_authoring_result` wraps the response afterward; `validate_interaction_contract` runs after the interaction checkpoint is committed. Its envelope failures therefore do not share the engine repair loop, and an invalid contract can have a ready checkpoint. | Same persisted ledger/checkpoint; `interaction:<interaction_id>` key. |
| Document composition | `AuthoringEngine` checks JSON schema with a no-op registered semantic validator. `_validate_composer_payload` then checks block coverage, allowlists and task-only blocks. When enabled, heuristic fallback follows either any `AuthoringEngineError` or these semantic errors. The broad exception branch includes transport exhaustion, budget exhaustion and missing-definition/configuration errors. | Same persisted ledger/checkpoint; `composition:<work_order_id>`. Heuristic fallback consumes one budget slot and commits a checkpoint. |
| Print teaching/form planning | Each planner owns a two-pass loop: transport failures retry without semantic repair context; validation/structured-output failures attach the prior response and errors to pass two. Teaching planning additionally performs deterministic normalizations before semantic validation. The provider Agent has `NO_OUTPUT_RETRY`; `run_llm` transport attempts are explicitly one for these calls. | These preparation/planning loops are outside the Learn output's `AuthoringEngine` work-item ledger/checkpoint path. Their attempt traces use per-attempt IDs, but the inspected functions do not wire `CallBudgetLedger` or `CheckpointStore`. Keep this planning boundary separate from the bounded P5 Learn writer change unless Sol says it is in scope. |

## Error classes as implemented

- Contract/schema/semantic validation is repairable inside the AuthoringEngine today when represented as `_validate_payload` errors. Post-engine writer/composer/interaction checks bypass that owner.
- Provider transport, timeout, overload and rate limit are identified separately by `classify_provider_error`/`run_llm`; they should never be included as semantic repair instructions. `AuthoringEngine` maps exhausted transport to `PROVIDER_TRANSPORT_EXHAUSTED`, but current provider-internal attempts are not individually reserved in its ledger.
- Auth, invalid request, quota, missing definition/input, incompatible approved input, budget exhaustion, lease loss, checkpoint incompatibility, and programming errors should terminate the current authored work item without semantic correction. User-level recoverability remains a visible outer retry decision, not an implicit model repair.
- Composer fallback is a declared degraded policy and consumes a budget slot, but current fallback eligibility is too broad. It should only follow explicitly permitted content/coverage failure after the bounded semantic repair allowance is exhausted, never transport, budget, auth, setup, approval, or programming failures.

## Smallest proposed implementation

1. Keep the shared AuthoringEngine as the sole semantic correction owner for Learn-authored capabilities, composition, document primitives, and interaction content. Move post-engine semantic checks into registered validators so a correction uses the same work-order ID, attempt budget and repair prompt.
2. Make provider dispatch accounting truthful. Disable the unmetered pydantic-ai output retry and V3 retry multiplication for this adapter path, or have every real nested dispatch reserve/record against the same work-order budget. Preferred narrow direction: one provider dispatch per `AuthoringProvider.invoke`, with transport retries reserved by AuthoringEngine. Surface structured-output validation as typed repair input to the engine so disabling the SDK retry does not turn correctable output into a terminal error. Sol should confirm this boundary before implementation.
3. For document writing, register `_payload_quality_errors` and normalization-level contract checks with the engine validator; remove the second post-engine failure branch. Only commit `node:` ready checkpoint after all checks pass.
4. For composition, register `_validate_composer_payload` as the engine semantic validator. Preserve exact closed per-block allowlists. If explicit heuristic fallback is enabled, allow it only after a semantic repair failure (`REPAIR_EXHAUSTED` or a typed semantic-invalid result); propagate transport, budget, definition/input, and unexpected exceptions. Its one declared fallback call continues to consume the same budget.
5. For interaction writing, validate model-authored prompt/config/feedback envelope in the engine validator. Run final backend-owned envelope validation before committing `interaction:` checkpoint; a checkpoint must never become ready for an invalid contract. Do not repair backend-assigned identity/provenance fields.
6. Leave the existing Print teaching/form two-pass planners outside this shared Learn work-item boundary for P5. They already separate transport retry from semantic correction and use explicit one-attempt provider transport policy; broadening those planners would be a separate ownership redesign, not required to stop nested retries in Learn authoring.

## Deterministic P5 gate matrix

1. Engine: invalid schema/semantic response followed by valid response makes exactly one repair call, carries the same work-order identity, and records one budget reservation per real provider dispatch.
2. Provider: structured-output failure reaches the engine's typed correction input with output retry disabled; transport/rate-limit failure makes no semantic-repair call and is accounted as a transport attempt.
3. Provider terminal classes: auth, quota, invalid request and unknown/programming failure are not retried as semantic corrections; budget exhaustion stops before another provider dispatch.
4. Document primitive: a schema-valid but quality-invalid first response is repaired by the same engine boundary; success commits the checkpoint once. Exhaustion leaves no ready checkpoint and returns a typed failure with repair/budget counts.
5. Composer: semantic allowlist/coverage failure is repaired by the engine; exhausted semantic failure may use explicitly enabled heuristic fallback, consumes one fallback budget slot, and commits `composition_mode=heuristic_fallback`. With fallback enabled, transport exhaustion, budget exhaustion, missing definition/input, auth and programming failures propagate without fallback or ready checkpoint.
6. Interaction: invalid authored config/envelope gets one same-work-item repair; a still-invalid final contract leaves its checkpoint non-ready. Valid contract replay returns the checkpoint without another provider call.
7. Recovery: ready compatible composition/node/interaction checkpoints are reused with zero provider calls; incompatible checkpoints fail closed and do not start a repair loop.
