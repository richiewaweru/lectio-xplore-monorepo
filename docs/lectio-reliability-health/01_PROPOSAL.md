# Proposal: preserve architecture, complete execution reliability

## Frozen decisions
Teaching Plan is the last shared instructional decision artifact. Learner actions are planned upstream and validated against YAML policy. Six ordinary primitives remain Paragraph, Heading, List, Figure, Table, Callout. Preserve shared document composer, shared ordinary writer, and shared authoring infrastructure. Learn owns interactions; Print owns paper treatments and PDF. Final documents are independently edited, and sibling generation starts from the approved Teaching Plan, never conversion of the other artifact. No revival of semantic component registries, v1 Learn salvage, or component_lectio. Mutable pedagogy remains in Markdown, mappings in YAML/JSON, invariants in code.

## Intended flow
Curriculum: Unit → lesson path/spec/skeleton → structure → structural approval → items → teaching plan → teaching approval → immutable revision reference.
Print: approved revision → admitted Print run → shared composer → ordinary node writes + Print task treatments/media → native assembly → stored editable Print document → explicit edits → PDF of that revision.
Learn: approved revision → admitted Learn run → shared composer → ordinary node writes + Learn interaction realization/media → LearnDocument v2 → stored editable draft → explicit publish → release → learner attempt/evaluation/analytics.
Approval, publication, assignment and export remain explicit operations where the product currently requires them. Do not turn generation completion into automatic publication. Preserve section/node identities and approved-item references.

## Ownership
Curriculum owns preparation decisions and states. Print and Learn own run graphs, policies, native persistence and completion decisions. Shared infrastructure supplies execution-record contracts, trace propagation, atomic budget/lease primitives and provider transport. Shared document services accept execution context; they do not select the sibling path or mutate its state. The app coordinates independent run admissions and presents aggregate status. Reuse existing code where it meets the contract; do not introduce a generic orchestration platform merely to rearrange functions.

## Durable execution contract
Define versioned stage definitions with stage_id, label, owner, dependencies, input/output schema versions, checkpoint granularity, timeout, budget policy, validator and permitted transitions. Distinguish stage definition, stage execution, work item and provider attempt. A run can have multiple active items. Approval waiting is separate from failure and does not hold a worker lease.
Stable run/work-item IDs are allocated and persisted before provider dispatch; retries reuse them. A composition checkpoint freezes ordered node IDs and the exact input identity. Checkpoints cover nodes, interactions, native task treatments, media jobs, assembly and export as appropriate. Persist validated output, completion and durable event together. A crash after commit must reuse the result. Partial streams are not completed content. Assembly must validate all required dependencies.
Do not hold a database transaction open for a model call. Use short claim/record/commit transactions. Fencing tokens reject stale workers. Cancellation prevents new calls and late result publication; in-flight provider charges may still occur. Capture unknown outcomes instead of assuming no charge.

## Idempotency
Caller-scoped request keys distinguish retries from intentional regeneration. Same key + same parameters returns the existing job/result; same key + different parameters is a conflict; regeneration gets a new key. Enforce database uniqueness, including simultaneous requests. Record retention policy and reject/reconcile late arrivals under documented rules. Publication, saves and export need operation identity plus expected document revision. No cross-owner result leakage. An idempotent repeated successful save must return its committed result rather than merely fail as a stale edit; a genuinely different stale save remains 409.
Reuse completed checkpoints only when teaching revision, input hash, composition identity, prompt/policy/schema and execution version are compatible. Deliberate upstream changes create a new run or explicitly invalidate affected downstream work; never reuse stale content silently.

## Attempts and policies
Default: 3 total provider calls for one logical authoring work item (initial + two additional calls), including transport failures, schema repair, semantic repair and fallback calls. Composer and each writer/interaction are distinct work items. This is an explicit initial product policy, not an industry mandate. Separate reason counters without multiplying the cap. Atomically reserve a call before dispatch; worker restarts preserve the count. Disable SDK retries or count every underlying call. Manual resume cannot reset budgets; any extension is explicit and audited.
Retry transient connection failures, eligible timeouts, temporary rate limits and provider overloads using bounded exponential backoff/jitter, provider Retry-After and an overall deadline. Provider-specific error types distinguish rate limits from quota/billing failures. Invalid output receives error-informed repair. Bad credentials, invalid request parameters, incompatible schemas, quota exhaustion and deterministic code errors need intervention rather than repeated identical calls. Conflict reconciliation and worker loss are not model repair. Unknown errors park visibly with diagnostics.
Fallback is declared and budgeted; preserve truthful composition_mode, reason, actual model and effective prompt hash. The baseline permits heuristic composition fallback; make it policy-controlled and visible, not silently removed or silently counted as LLM success. Normal live proof must demonstrate LLM composition. Preserve existing visual_pending/media semantics; isolate retries of failed assets from completed text.

## Observability and API
Admit long runs quickly with run ID and status/events links. Persist events with ordered sequence; SSE reconnect replays missed events, with snapshot recovery if retention expired. GET status is authoritative and includes active items, completed/total counts, retry schedule, allowed actions and revisions. Events include run/path/stage/item/attempt/time/error category. Propagate trace identity to shared calls. Record actual model, provider request ID, prompt/policy hashes, tokens and estimated cost using a versioned price record. Unknown usage remains unknown. No secrets/raw learner responses in general logs; authorized detailed diagnostics only. Frontend progress shows actual counts or indeterminate waits, never fabricated percentages.

## Frontend
Keep thin routes composing curriculum panels, Print generation/editor/export, Learn authoring, and learner runtime. Extract API actions, subscriptions, domain state and rendering separately. Scope caches and operation state by owner/run/document/revision. The server authorizes transitions; UI derives available actions. Reconnect without duplicate subscriptions; ignore stale/out-of-order updates; unsubscribe on navigation. Preserve dirty edits during progress refresh, show revision conflicts without overwriting, and keep retry/resume/regenerate distinct. Shared UI controls and event transport are allowed; product-specific stores cannot import sibling domain internals.

## Delivery approach
P00 early browser readiness and baseline → P01 repository health → P02 execution records/stages/idempotency → P03 checkpoint recovery and attempt budgets → P04 API/telemetry → P05 frontend separation/recovery → P06 live and independent verification. Use additive migrations, dry-run representative existing records, and define rollback before switching callers. Existing artifacts remain readable. Gate each slice; don't combine unrelated product redesigns or broad dependency upgrades.
